# Bug Register — Registration / OTP / Email Verification Flow

| # | Bug / Issue | Location | Status | Fix |
|---|-------------|----------|--------|-----|
| 1 | **Stuck on OTP page**: a user who registers, lands on the OTP page, then navigates to /login cannot proceed. `authenticate_user` returns `None` for unverified users, so login fails with 401 and gives no path back to OTP. The user is stuck — they can neither log in nor return to OTP (the OTP code/email they had is orphaned). | `app/services/auth.py` (`authenticate_user`) | **Fixed** | `authenticate_user` no longer returns `None` for unverified users. It now returns the user so the login router can branch. The login route checks `is_verified`: if valid credentials but email unverified, it **resends a fresh OTP** and returns HTTP 403 with `{"detail": "email_not_verified", "resend_otp": true}` so the frontend redirects to the OTP page for reverification. |
| 2 | **Unverified users can reach the dashboard**: `get_current_user` validates the JWT but never checks `is_verified`. A user who somehow holds a token (e.g. issued before verification was enforced, or via Google OAuth which skips OTP) can access /tasks, /users, etc. without verifying email. | `app/dependencies.py` (`get_current_user`) | **Fixed** | After resolving the JWT, `get_current_user` raises HTTP 403 `{"detail": "Email not verified. Please verify your email to access the dashboard."}` when `user.is_verified` is False. |
| 3 | **No signal for frontend to redirect to OTP**: login returned a generic 401 "Invalid email or password, or email not verified." which hides whether credentials were wrong or the email just isn't verified. Frontend cannot decide whether to show "wrong password" or "go verify email". | `app/routers/auth.py` (`login`) | **Fixed** | Distinguished error cases: wrong credentials → 401 "Invalid email or password."; valid credentials but unverified → 403 with `email_not_verified` code + `resend_otp: true`. |
| 4 | **Test seed users are unverified**: `tests/conftest.py` seeds users with `is_verified=False` (default). With fix #2 enforced, the existing test fixtures (`admin_headers`, `user1_headers`, ...) would fail because the seeded users cannot pass the new verification check. | `tests/conftest.py` (`seeded_users`) | **Fixed** | Seeded `admin`, `user1`, `user2` now created with `is_verified=True`. |
| 5 | **Google login imports `settings` at module scope inside function body**: `google_auth` imports `settings.google_client_id` via the module-level `settings` import at top of file. This is fine functionally, but for consistency with other functions in the codebase (e.g. `send_otp_email` imports `settings` inside the function), the `google_auth` function uses the top-level `settings` reference which is shared across the app. No functional issue. | `app/routers/auth.py` (`google_auth`) | **Acknowledged** | Using module-level `settings` is correct since it's a pydantic-settings singleton. No functional change required. |
| 6 | **Resend OTP endpoint lacks user-ownership check**: `resend_otp` verifies email exists and is unverified but does not confirm the caller owns the email. Since OTP verification is tied to email (not user ID), this is acceptable for the registration flow. | `app/routers/auth.py` (`resend_otp`) | **Acknowledged** | OTP is email-scoped; ownership enforcement is a future enhancement, not a blocker for email verification. |
| 7 | **`verify-otp` issues JWT to unverified users**: `verify-otp` returns a JWT after marking the user verified. This is expected and correct — OTPs are only sent to unverified users, so a valid OTP implies the user completed verification. | `app/routers/auth.py` (`verify_otp`) | **No fix needed** | Behavior is correct and consistent with the registration flow. |

## Summary
- Bug 1: Fixed — login now re-sends OTP and returns `email_not_verified` → frontend goes to OTP page.
- Bug 2: Fixed — `get_current_user` enforces `is_verified` before any protected route.
- Bug 3: Fixed — login distinguishes wrong-credentials (401) from unverified-email (403).
- Bug 4: Fixed — test seed users marked verified so existing tests keep passing.
- Bug 5: Acknowledged — no functional change needed (module-level `settings` singleton is correct).
- Bug 6: Acknowledged — email-scoped OTP is by design; ownership enforcement deferred.
- Bug 7: No fix needed — behavior is correct.

All changes are backward compatible (existing verified users and OAuth flows continue to work). The login flow now guides unverified users back to the OTP page, and the dashboard is protected by email verification.
